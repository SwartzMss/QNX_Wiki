            Before we start talking about threads, processes, time slices, and all the other wonderful scheduling concepts, let's establish an analogy.

          • The kernel's role

            The house analogy is excellent for getting across the concept of synchronization, but it falls down in one major area. In our house, we had many threads running simultaneously. However in a single-processor system, only one thing can run at once.

            • Single CPU

              Let's look at what happens in the economy case where we have one CPU in the system. In this case, only one thread can run at any given point in time. The kernel decides (using a number of rules, which we'll see shortly) which thread to run, and runs it.

            • Multiple CPU (SMP)

              If you buy a system that has multiple, identical CPUs all sharing memory and devices and being managed by the same OS instance, you have an SMP box (SMP stands for Symmetrical Multi Processor, with the symmetrical part indicating that all the CPUs in the system are identical).

            • The kernel as arbiter

              So who decides which thread is going to run on a given CPU at a given instant in time? That's the kernel's job. The kernel determines which thread should be using the CPU at a particular moment, and context-switches to that thread. Let's examine what the kernel does with the CPU.

Kernel states

QNX SDP8.0Getting Started with the QNX OSDeveloperUser

We've been talking about running, ready, and blocked loosely—let's now formalize these thread states.

RUNNING
QNX OS's RUNNING state simply means that the thread is now actively consuming CPU cycles. On an SMP system, there will be multiple threads running; on a single-processor system, there will be one thread running.
READY
The READY state means that this thread could be running right now—except that it's not, because other threads (at the same or higher priorities) are running. If two threads were capable of using a particular CPU, one thread at priority 10 and one thread at priority 7, the priority 10 thread would be RUNNING, and the priority 7 thread would be READY, assuming there was no other CPU on which it could run at the moment. This situation would arise for the latter (priority 7) thread whenever there were other higher-priority threads running on all the processors included in its processor affinity setting (runmask). Although that thread could in principle run on any of these processors, it would not be scheduled for execution in practice because of its lower priority (and thus remain in the READY state).
The blocked states
What do we call the blocked state? The problem is, there's not just one blocked state. There are in fact many, many blocking states.

Why so many? Because the kernel keeps track of why a thread is blocked.

We saw two blocking states already—when a thread is blocked waiting for a mutex, the thread is in the MUTEX state. When a thread is blocked waiting for a semaphore, it's in the SEM state. These states simply indicate which queue (and which resource) the thread is blocked on.

If a number of threads are blocked on a mutex (in the MUTEX blocked state), they get no attention from the kernel until the thread that owns the mutex releases it. At that point one of the blocked threads is made READY, and the kernel could make a rescheduling decision for the same CPU on which the previous mutex owner was running.

Why could? The thread that just released the mutex could very well still have other things to do and have a higher priority than that of the waiting threads that have runmasks that include the CPU in question. In this case, we go to the second rule, which states, The highest-priority ready thread will run, meaning that the scheduling order has not changed—the higher-priority thread continues to run.
